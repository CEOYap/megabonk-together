# BepInEx (IL2CPP)

`BepInEx.Unity.IL2CPP` 6.0.0-be (bleeding edge), pulled from `nuget.bepinex.dev`. This is
**BepInEx 6, not 5** — the entry point is `BasePlugin` with an override of `Load()`, not
`BaseUnityPlugin` with `Awake()`.

Entry point: `src/plugin/Plugin.cs`.

```csharp
[BepInPlugin(MyPluginInfo.PLUGIN_GUID, MyPluginInfo.PLUGIN_NAME, MyPluginInfo.PLUGIN_VERSION)]
public class Plugin : BasePlugin
{
    public static Plugin Instance = null!;
    internal static new ManualLogSource Log;

    public override void Load() { /* ... */ }
}
```

`MyPluginInfo` is generated by the `BepInEx.PluginInfoProps` package from the csproj
`<AssemblyName>`, `<Product>` and `<Version>` — **bump the version in the csproj**, never
hardcode it.

## Load() order

`Load()` must do these in order; each depends on the previous:

1. `Instance = this;` and `Log = base.Log;`
2. `ModConfig.Initialize(Config);` — before anything reads a setting
3. `ClassInjector.RegisterTypeInIl2Cpp<T>()` for every injected MonoBehaviour
4. Build the DI host and assign `Plugin.Host`
5. Harmony patching / component creation

```csharp
var builder = new HostBuilder();
builder.ConfigureServices(services =>
{
    services.AddSingleton(Log);
    services.AddSingleton<IWebsocketClientService, WebsocketClientService>();
    services.AddSingleton<IUdpClientService, UdpClientService>();
    // ... one line per service
});
Host = builder.Build();
```

`Plugin.Services => Host.Services` is the single resolution point. A service that isn't
registered here throws from `GetRequiredService` inside a MonoBehaviour `Awake()` — which under
IL2CPP looks like a component that silently never runs.

## Configuration

All settings live in `Configuration/ModConfig.cs` as `public static ConfigEntry<T>` with a
private setter, bound once in `Initialize(ConfigFile config)`:

```csharp
PlayerName = config.Bind(
    "Player",
    "PlayerName",
    "Player",
    "Your display name shown to other players. Please be respectful!"
);
```

Sections in use: `Player`, `Network`, `Updates`, plus the netplay options. Two entries are
internal bookkeeping rather than user settings — `ShowChangelog` and `PreviousVersion` — and say
so in their description. Follow that convention if you add another.

Read a value with `.Value`; it's live, so a user editing the `.cfg` mid-session is reflected.
Don't cache `.Value` in a static at load time unless you intend to freeze it.

Network defaults worth knowing:

- `ServerUrl` → `wss://megabonk-together-matchmaking.balatro-vs-matchmaking.eu`
- Local testing → `ws://127.0.0.1:5000` (matches the server project's default)
- `RDVServerPort` → `5678`

## Logging

```csharp
Plugin.Log.LogInfo($"Plugin {MyPluginInfo.PLUGIN_GUID} is loaded!");
Plugin.Log.LogWarning(ex);
Plugin.Log.LogError(...);
```

Output goes to `BepInEx/LogOutput.log` in the game folder. Because there is no debugger against
a shipped IL2CPP build, the log is the primary diagnostic — but it is also a real per-frame cost.
**Never log inside `Update()`, a per-frame patch, or the packet receive path.** Recent history
bears this out: commit `041881b` added chest-open logging to chase a bug and the following
release was a performance pass.

For on-screen debugging during a session, use `Helpers/ScreenTextHelper.cs` rather than log spam.

## Update and changelog flow

- `AutoUpdaterService` checks GitHub releases at startup when `CheckForUpdates` is true.
  Thunderstore builds ship with this path disabled — see the `THUNDERSTORE` compile constant in
  the **build-and-release** skill.
- `ChangelogService` reads `src/plugin/CHANGELOG.toml` (copied to output via
  `CopyToOutputDirectory`) and shows entries when `PreviousVersion` differs from the current one.

**Releasing means editing three places:** the csproj `<Version>`, a new `[version."X.Y.Z"]` block
in `CHANGELOG.toml`, and the changelog section of `README.md`.

## Teardown

The plugin does not unload, but a *session* ends. Anything hooked in must be undone when a run
ends or the player returns to the menu:

- restore saved `Il2CppSystem.Action` delegates (`originalDiedAction`, `originalWeaponAddedAction`,
  `originalStatUpdateAction`)
- reset the `CAN_*` gates
- `IUdpClientService.Reset()` / `GameOver()`
- cancel the `CancellationTokenSource`

Leaks here show up as "mod breaks singleplayer after playing multiplayer" — a recurring class of
bug in this project.

## Common mistakes

1. **Writing BepInEx 5 code** (`BaseUnityPlugin`, `Awake()`) — wrong major version.
2. **Hardcoding the version string** instead of using `MyPluginInfo`.
3. **New service or injected type not registered** → silent no-op.
4. **Reading config before `ModConfig.Initialize`** → null entry.
5. **Logging in a hot path** → measurable FPS loss.
6. **Bumping the csproj version without a `CHANGELOG.toml` entry** → the in-game changelog shows
   nothing after an update.
